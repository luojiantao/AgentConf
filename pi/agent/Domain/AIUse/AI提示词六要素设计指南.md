# AI 提示词六要素设计指南

## 1. 文档目的

本文说明如何使用以下六个要素设计结构清晰、可复用、可验证的 AI 提示词：

```text
Prompt = Role + TechStack + Domain + Requirement + Constraints + Acceptance
```

这套模型把“稳定能力”和“本次任务”分开，避免把角色、技术栈、业务知识和临时需求全部塞进一个角色定义中。适用于代码开发、架构设计、配置修改、问题排查、技术评审和文档生成等任务。

## 2. 六要素总览

| 要素 | 中文含义 | 回答的核心问题 | 变化频率 |
|---|---|---|---|
| `Role` | 角色 | AI 以什么身份、职责和判断视角工作？ | 低 |
| `TechStack` | 技术栈 | AI 使用什么技术、版本和工程规范工作？ | 中 |
| `Domain` | 业务知识 | AI 需要理解哪些业务对象、流程和规则？ | 中 |
| `Requirement` | 任务需求 | 这一次具体要解决什么问题、交付什么结果？ | 高 |
| `Constraints` | 执行约束 | 哪些边界不能突破，哪些规则必须遵守？ | 高 |
| `Acceptance` | 验收标准 | 用什么客观证据判断任务已经完成？ | 高 |

六个要素可以进一步分为两层：

```text
可复用能力配置 = Role + TechStack + Domain
单次任务定义   = Requirement + Constraints + Acceptance
最终提示词     = 可复用能力配置 + 单次任务定义
```

## 3. Role：角色

### 3.1 定义

`Role` 定义 AI 的身份、职责范围、思考视角和工作方式。它决定 AI 应该站在什么位置分析问题，而不是负责罗列全部技术知识。

### 3.2 应包含的内容

- 角色名称，例如系统架构师、开发工程师、测试工程师。
- 主要职责，例如设计、实现、评审、验证或交付。
- 决策视角，例如优先关注可靠性、可维护性或用户体验。
- 输出风格，例如先给结论、提供证据、明确风险和权衡。
- 职责边界，例如只做评审，不直接修改代码。

### 3.3 不应包含的内容

- 大量框架、数据库和工具版本，这些属于 `TechStack`。
- 具体业务对象和业务流程，这些属于 `Domain`。
- 本次要修改的功能，这些属于 `Requirement`。
- “构建必须通过”等完成条件，这些属于 `Acceptance`。

### 3.4 推荐写法

```text
你是一名系统架构师，负责分析系统边界、模块职责、依赖关系和技术风险。
做技术决策时，需要说明候选方案、主要权衡、推荐理由和迁移影响。
未经明确要求，不直接进行代码实现。
```

### 3.5 常见错误

错误写法：

```text
你是 BionanoSemi 专家，精通所有代码、配置、半导体工艺、RabbitMQ、MongoDB 和 WPF，负责解决所有问题。
```

问题在于角色范围过大，同时混入了技术栈和业务知识，无法判断具体职责，也不利于在其他项目中复用。

## 4. TechStack：技术栈

### 4.1 定义

`TechStack` 描述项目允许使用的语言、框架、运行平台、数据库、通信技术、工具链和编码规范。它决定 AI 应该使用什么技术手段完成任务。

### 4.2 应包含的内容

- 编程语言和目标框架。
- UI、通信、数据库和依赖注入框架。
- 关键版本及兼容要求。
- 构建、测试、日志和部署工具。
- 项目采用的架构模式和代码规范。
- 明确禁止使用的技术或版本。

### 4.3 不应包含的内容

- CJ、PJ、UJ 等业务对象，这些属于 `Domain`。
- “修复调度异常”等当前任务，这些属于 `Requirement`。
- “不得修改公共接口”等本次边界，这些属于 `Constraints`。
- “测试全部通过”等完成条件，这些属于 `Acceptance`。

### 4.4 BionanoSemi 示例

```text
- 目标框架：.NET Framework 4.8.1
- 桌面 UI：WPF、XAML、Prism 7.x、DryIoc
- 分布式通信：RabbitMQ、gRPC
- 数据存储：MongoDB、InfluxDB 3.x
- 日志：Serilog
- 代码风格：4 空格缩进、Allman 花括号、公共 API 使用 XML 注释
- 除 Tool/BionanoSemiWebServer 外，不使用 .NET 6+ API
```

### 4.5 常见错误

- 使用“采用最新版本”这类无法确定兼容性的描述。
- 只写技术名称，不写版本和使用边界。
- 将目标技术和候选技术混在一起，没有说明最终选择。
- 技术栈与仓库实际目标框架冲突。

## 5. Domain：业务知识

### 5.1 定义

`Domain` 描述 AI 完成任务时必须理解的业务语言、对象关系、流程、状态、规则和不变量。它回答“这个系统中的概念意味着什么”。

### 5.2 应包含的内容

- 业务术语及其准确含义。
- 核心实体、属性和关系。
- 业务流程、状态机和生命周期。
- 必须始终成立的业务规则。
- 异常处理、互锁和安全规则。
- 与任务相关的项目目录、配置和服务职责。

### 5.3 不应包含的内容

- C#、WPF、RabbitMQ 等实现技术，这些属于 `TechStack`。
- “新增一个功能”等当前目标，这些属于 `Requirement`。
- 临时修改范围和禁止事项，这些属于 `Constraints`。
- 尚未确认的推测。推测必须明确标记为假设，不能当作业务事实。

### 5.4 BionanoSemi 示例

```text
- CTC 使用三级 Job：Control Job、Process Job、Unit Job。
- Control Job 负责批次级协调，Process Job 表示单片晶圆完整流程，Unit Job 表示单个单元操作。
- 配方分为 Control Recipe、Process Recipe、Unit Recipe 和 Robot Recipe。
- 模块 IO 的 IoKey 必须与 conf-io.xml 中 Item Name 的前缀一致。
- 修改 Conf.json 或 conf-io.xml 后，需要重启对应服务才能生效。
```

### 5.5 常见错误

- 把整个项目说明全部放入提示词，造成无关上下文过多。
- 同一个业务规则在多个角色中重复维护，更新时容易不一致。
- 将历史经验当成当前事实，没有核对代码或配置。
- 只描述名词，不说明对象之间的关系和约束。

## 6. Requirement：任务需求

### 6.1 定义

`Requirement` 描述本次任务要解决的问题、目标对象、期望行为和交付物。需求应该说明“做什么”和“为什么做”，但不应无依据地提前锁死实现方式。

### 6.2 应包含的内容

- 当前问题或业务目标。
- 影响的用户、模块、服务或流程。
- 当前行为与期望行为。
- 明确的输入和需要交付的结果。
- 已知错误、日志、复现路径或需求来源。
- 任务优先级和必要背景。

### 6.3 不应包含的内容

- 与本次任务无关的项目背景。
- 没有验证依据的根因结论。
- “不能修改某文件”等边界，这些属于 `Constraints`。
- “构建通过、测试通过”等验收条件，这些属于 `Acceptance`。

### 6.4 推荐写法

```text
CTC 在重复收到同一条 Process Job 状态消息时，可能重复推进 PJ 状态。
请定位重复处理路径并修复，使相同业务消息只能生效一次，同时保留正常状态推进能力。
交付物包括代码改动、根因说明和验证结果。
```

### 6.5 常见错误

错误写法：

```text
优化一下调度，让它稳定运行。
```

这段需求没有说明当前问题、目标对象、期望行为和交付物，AI 无法判断任务是否完成。

## 7. Constraints：执行约束

### 7.1 定义

`Constraints` 定义执行任务时不能突破的边界，以及必须遵循的安全、兼容、范围和流程规则。约束限制“可以怎么做”。

### 7.2 应包含的内容

- 允许和禁止修改的项目、目录、文件或接口。
- 兼容性要求和不可升级的依赖。
- 明确的非目标，防止任务范围扩张。
- 性能、实时性、安全和设备互锁限制。
- 数据迁移、服务重启和外部系统限制。
- 是否允许联网、安装依赖、启动设备或修改外部状态。
- 必须遵循的仓库规范和审批流程。

### 7.3 不应包含的内容

- “实现某功能”等目标，这些属于 `Requirement`。
- “测试通过”等完成判定，这些属于 `Acceptance`。
- 纯技术事实，例如项目使用 WPF，这些通常属于 `TechStack`。

### 7.4 BionanoSemi 示例

```text
- 不修改现有公共消息协议和公共接口。
- 不升级 .NET Framework、Prism 或 RabbitMQ 依赖。
- 不修改 Third/ 下的第三方代码。
- 不进行与问题无关的重构。
- 未连接真实设备时，不执行可能触发机械运动的运行验证。
- 保持现有 Conf.json 配置兼容。
```

### 7.5 常见错误

- 使用“不要影响其他功能”这种无法操作和验证的宽泛描述。
- 不说明配置修改是否允许重启服务。
- 忽略 PLC、机器人和真实设备的安全边界。
- 约束相互冲突，却没有说明优先级。

## 8. Acceptance：验收标准

### 8.1 定义

`Acceptance` 定义任务完成后必须提供的客观结果和验证证据。它回答“怎样才算完成”，应尽量可执行、可观察、可重复。

### 8.2 应包含的内容

- 静态代码检查结果。
- 构建、单元测试或集成测试结果。
- 正常路径、异常路径和边界场景的预期行为。
- 性能、响应时间、吞吐量或资源占用指标。
- 日志、截图、报告或输出文件等交付证据。
- 受硬件限制无法自动验证时的手工验证步骤。

### 8.3 不应包含的内容

- “代码质量高”“运行正常”等主观判断。
- 无法在目标环境测量的虚假精确指标。
- 新增功能要求，这些应回到 `Requirement`。
- 修改范围限制，这些属于 `Constraints`。

### 8.4 BionanoSemi 示例

```text
- 受影响的 C# 项目能够在 Debug 配置下构建通过。
- 自动化测试证明重复消息不会导致 PJ 状态重复推进。
- 单条正常消息仍能推进一次 PJ 状态。
- 非法状态转换被拒绝，并记录包含 PJ 标识和当前状态的日志。
- 无真实 RabbitMQ 或设备环境时，提供可复现的模拟验证步骤。
```

### 8.5 常见错误

错误写法：

```text
功能正常，没有问题，代码尽量优雅。
```

这类描述没有可执行的检查方法，也没有明确预期结果，不能用于验收。

## 9. 六要素之间的边界

| 容易混淆的要素 | 区分方法 |
|---|---|
| `Role` 与 `TechStack` | 角色是身份和职责；技术栈是完成任务的技术手段。 |
| `TechStack` 与 `Domain` | 技术栈描述软件技术；业务知识描述系统中的业务对象和规则。 |
| `Domain` 与 `Requirement` | 业务知识长期有效；需求只描述当前任务。 |
| `Requirement` 与 `Constraints` | 需求说明要做什么；约束说明不能怎么做或必须遵守什么。 |
| `Requirement` 与 `Acceptance` | 需求描述目标；验收标准提供完成目标的验证证据。 |
| `Constraints` 与 `Acceptance` | 约束在执行前限制方案；验收在执行后判断结果。 |

判断一条信息应该放在哪里时，可以使用以下方法：

- 换一个项目后仍然适用，通常属于 `Role`。
- 换一个业务模块后仍然适用，但换技术后不适用，通常属于 `TechStack`。
- 换一个任务后仍然适用，但换业务系统后不适用，通常属于 `Domain`。
- 只对当前任务有效，通常属于 `Requirement`、`Constraints` 或 `Acceptance`。

## 11. BionanoSemi 完整示例

````md
# Role

你是一名高级软件开发工程师，负责定位根因、实施最小范围修复并提供验证证据。
分析时区分已知事实、合理假设和待验证信息；实现时优先保证设备控制系统的可靠性和可维护性。

# TechStack

- .NET Framework 4.8.1、C#、WPF、Prism 7.x、DryIoc
- RabbitMQ 分布式消息通信
- MongoDB 数据存储和 Serilog 日志
- 4 空格缩进、Allman 花括号

# Domain

- CTC 使用 Control Job、Process Job、Unit Job 三级调度模型。
- Process Job 表示单片晶圆跨单元的完整处理流程。
- PJ 状态只能按照合法状态路径推进。
- RabbitMQ 消息可能因重试或网络恢复而重复到达，业务处理需要保证幂等。

# Requirement

CTC 在重复收到同一条 Process Job 状态消息时，可能重复推进 PJ 状态。
请定位重复处理路径并修复，使相同业务消息只能生效一次，同时保留正常状态推进能力。
交付代码改动、根因说明和验证结果。

# Constraints

- 不修改现有公共消息协议和公共接口。
- 不升级第三方依赖。
- 不修改 `Third/` 下的代码。
- 不进行无关重构。
- 保持现有配置文件兼容。
- 未连接真实设备时，不执行可能触发设备动作的运行测试。

# Acceptance

- 受影响项目在 Debug 配置下构建通过。
- 自动化测试或可重复模拟证明重复消息不会重复推进 PJ 状态。
- 单条正常消息仍然只推进一次状态。
- 非法状态转换被拒绝，并记录包含 PJ 标识和状态信息的日志。
- 最终报告列出修改文件、验证结果和未验证的现场条件。
````

## 12. 编写和评审检查表

提交提示词前，逐项检查：

- [ ] `Role` 只描述身份、职责、视角和工作方式。
- [ ] `TechStack` 包含实际版本和兼容范围，没有使用模糊的“最新技术”。
- [ ] `Domain` 只保留与任务相关的业务事实和规则。
- [ ] `Requirement` 明确描述当前问题、目标行为和交付物。
- [ ] `Constraints` 明确修改范围、非目标、兼容和安全边界。
- [ ] `Acceptance` 中每一项都有可观察的预期结果或证据。
- [ ] 六个部分之间没有明显重复或相互冲突。
- [ ] 未确认的信息被标记为假设或待验证项。
- [ ] 删除了所有未填写的模板占位内容。

## 13. 冲突处理原则

当提示词内部出现冲突时，按照以下顺序处理：

1. 安全、权限和仓库强制规则。
2. 明确的 `Constraints`。
3. 当前 `Requirement`。
4. `Acceptance` 中的完成条件。
5. `TechStack` 和 `Domain` 提供的项目背景。
6. `Role` 的一般工作偏好。

如果高优先级约束使需求或验收标准无法完成，应停止执行并明确报告冲突，不能静默忽略约束或擅自降低验收标准。
