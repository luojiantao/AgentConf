# AI 方案执行器

## 目标

作为方案执行的唯一对外入口，接收以下任一方案并完成实现、验证和交付：

1. **已获 master 确认的面向人类决策方案**：先在本执行流程内部按 `$ai-plan-converter` 的规则转换为 executor-ready 方案，再实施代码。
2. **已经由 `$ai-plan-converter` 生成的 executor-ready 方案**：跳过转换，直接实施代码。

两种输入都必须遵守方案中的目标、非目标、执行约束、修改范围、验收标准、静态校验、运行验证和最终交付要求。

## 对外工作流

master 只需要手动调用两个对外入口：

```text
$ai-plan-doc-writer
    ↓
面向人类的方案
    ↓ master 判断和确认
$ai-plan-executor
    ├─ 输入人类方案：内部自动执行 ai-plan-converter 规则
    └─ 输入 executor-ready 方案：跳过转换
            ↓
        AI Agent 修改代码、验证和交付
```

master **不需要**在默认路径中手动调用 `$ai-plan-converter`。

`$ai-plan-converter` 仍然保留为可选的独立入口，仅当 master 希望在修改代码前审查“具体改哪些文件、函数和类型”时使用：

```text
$ai-plan-converter 人类方案.md
    ↓
人类审查 executor-ready 方案
    ↓
$ai-plan-executor 人类方案.execution.md
```

## 职责边界

本 skill 是执行器，不是业务决策器。它可以在内部完成方案执行化转换，但不得：

- 绕过人工确认直接执行面向人类的方案；
- 改变 master 已确认的目标、推荐方案、非目标或业务取舍；
- 自行发明未确认的业务规则；
- 用方案外重构替代方案执行；
- 把无法确认的代码事实伪装成已确认内容。

如果内部转换发现需要重新做业务决策，必须停止并询问 master；不能因为转换是“内部步骤”就跳过这个安全闸门。

遵循 `Doc/AIPrompt/AI提示词六要素设计指南.md` 定义的边界：

```text
Role + TechStack + Domain + Requirement + Constraints + Acceptance
```

`Role` 只提供身份、职责、判断视角、工作方式和职责边界。不能把技术栈、业务知识、本次需求、执行约束或验收标准解释为角色职责。

## 执行原则

- 先完整读取输入方案并判断方案类型，再决定是否进行内部转换；不要只看标题或局部步骤就开始改文件。
- 输入是面向人类方案时，必须先确认其已获 master 确认，再按 `$ai-plan-converter` 的规则完成执行化转换。
- 输入是 executor-ready 方案时，必须确认来源方案状态为 `已确认`、转换状态为 `已转换`，再开始实现。
- 内部转换和代码实现必须在同一个 `plan-executor` Agent 会话中连续完成；master 不需要手动传递中间文件。
- 严格按最终 executor-ready 方案执行，不做方案外重构、统一格式化、无关清理或风格迁移。
- 如果方案与现有代码冲突，先说明冲突；只有不改变目标和边界的局部文件路径或签名偏差才能记录后继续。
- 运行验证不能替代代码静态校验；无法运行或无法确认的内容必须列入剩余风险。
- 不删除用户已有改动，不回滚无关文件，不把前一阶段角色带入后一阶段。

## Subagent 执行协议

本 skill 的主会话是协调器，不直接实施代码。模型确认后，通过全局 user scope 委派一个 `plan-executor` Agent 完成完整流程；主会话负责模型确认、委派、进度接收、中止处理和最终回传。

### 模型确认

在读取实现代码、修改任何文件或启动执行 Agent 前，必须先向 master 询问本次执行使用的精确模型，格式为 `provider/model`，例如 `3r/gpt-5.6-luna`。模型可通过当前 Pi 的 `/model` 或 `pi --list-models` 确认。

- 不得静默使用默认模型、上一次模型或 Agent 文件中的模型。
- master 指定后，向 master 回显将使用的精确模型，并保持该模型贯穿本次执行的全部阶段。
- master 说“使用当前模型/默认模型”时，先解析并明确当前的 `provider/model`，再继续。
- 模型不存在、不可用、未认证或 master 未确认时，停止，不读取实现代码、不修改文件。
- 执行中不得自动换模型；需要换模型时先中止本次执行，再由 master 重新确认并启动。

### 委派完整执行

模型确认后，使用全局 user scope 调用 `subagent`。这是唯一的实现委派：

```json
{
  "agent": "plan-executor",
  "agentScope": "user",
  "model": "<master 已确认的 provider/model>",
  "task": "完整读取方案：<plan path>。遵守 C:/Users/41290/.pi/agent/skills/ai-plan-executor/SKILL.md。先判断输入是已确认的面向人类决策方案还是 executor-ready 方案：如果是人类方案，先在本子会话内按 C:/Users/41290/.pi/agent/skills/ai-plan-converter/SKILL.md 完成执行化转换，并将转换结果作为本次执行的内部方案；转换通过后继续完成代码阅读、修改、静态校验、运行验证和最终报告。如果已经是 executor-ready 方案，跳过转换直接执行。除非遇到方案规定的阻塞或收到中止信号，不要提前结束，不要再委派另一个 plan-executor。",
  "cwd": "<当前工作目录>"
}
```

- 必须使用 `plan-executor`，不得把完整执行委派给 `scout`、`planner` 或 `worker`。
- 当输入是人类方案时，转换和实现必须在同一个被委派的 `plan-executor` 会话内完成，不得要求 master 再调用 `$ai-plan-converter`。
- 子 Agent 必须完整读取本 skill、输入方案以及需要时的 `$ai-plan-converter` skill，再按输入类型执行。
- `plan-executor` 已经由父会话完成委派；它读取本 skill 时不得递归启动另一个 `plan-executor`，也不得把内部转换再委派出去。
- 主会话等待 `subagent` 工具结束，不在子 Agent 执行期间自行修改同一方案范围的文件。
- 如果全局 subagent 扩展、`plan-executor` Agent 或模型参数不可用，停止并报告，不静默回退到主会话直接实现。

### 持续执行与当前会话回传

子 Agent 必须持续执行到以下任一终点：

- 方案转换、代码实现和可执行的静态/运行验证全部完成；
- 方案规定的阻塞条件出现；
- master 主动中止；
- 子进程或模型发生不可恢复错误。

内部转换成功时，必须在最终报告中说明：

- 输入方案类型；
- 来源方案路径和人工确认状态；
- 转换是否完成；
- 是否生成或保留了 `.execution.md` 中间文档；
- 转换阶段发现的代码事实、假设和局部偏差。

完成后，`subagent` 工具结果必须返回当前主会话。主会话保留执行状态、模型、阶段结果、修改文件、验收、验证和剩余风险，再向 master 汇报。

### 中止处理

在交互式 Pi 中，master 可以使用 `Escape` 中止当前 Agent 回合。Pi 的 abort signal 会传递到 subagent 扩展，扩展终止正在运行的子 Pi 进程，并将状态标记为 `aborted`。

中止后必须：

- 停止新的转换、修改、测试和验证动作；
- 返回已经完成的转换阶段、当前阶段、已修改文件和未完成步骤；
- 说明工作区可能处于中间状态的风险；
- 不自动重试、不自动换模型、不自动续跑。

只有 master 明确要求继续时，才能以新的执行请求重新开始；重新开始前必须重新确认模型和当前工作区状态。

## 执行流程

### 1. 输入方案识别

先完整读取用户指定的方案 Markdown，判断它属于哪一类：

#### 面向人类的决策方案

通常包含以下标志：

- `方案状态`；
- `问题定义`；
- `候选方案`；
- `方案对比`；
- `推荐方案`；
- `人工确认记录`；
- 没有完整的 `修改范围`、`函数级修改设计` 和 `代码静态校验`。

处理规则：

1. 确认 `方案状态` 为 `已确认`，或 master 在当前请求中明确确认并授权执行。
2. 如果方案仍是 `待人工确认`，立即停止，不读取实现代码、不修改文件。
3. 在本执行流程内部完整执行 `$ai-plan-converter` 的转换规则。
4. 转换必须先完成，且转换结果通过 executor-ready 检查后，才能进入实现阶段。

#### executor-ready 执行方案

通常包含以下标志：

- `来源决策方案`；
- `来源方案状态`；
- `转换状态`；
- `修改范围`；
- `新增类与结构体设计`；
- `函数级修改设计`；
- `代码静态校验`；
- `执行入口提示`。

处理规则：

1. 确认 `来源方案状态` 为 `已确认`。
2. 确认 `转换状态` 为 `已转换`。
3. 确认方案不是模板空值或半成品。
4. 直接进入执行方案读取和角色预检。

如果无法判断方案类型，先停止并说明输入格式不明确。

### 2. 内部转换阶段（仅人类方案输入）

内部转换必须严格遵守：

- `C:\Users\41290\.pi\agent\skills\ai-plan-converter\SKILL.md`；
- 项目规则和 `AGENTS.md`；
- 六要素指南；
- 当前角色目录；
- executor-ready 执行方案模板。

转换阶段必须完成：

1. 阅读已确认的人类方案；
2. 阅读当前代码、配置、测试、调用方和项目知识；
3. 核对目标、非目标、约束、不变量和失败路径；
4. 定位准确的文件、类型、函数、接口和验证入口；
5. 建立“决策条目 → 实现步骤 → 修改对象 → 验收标准”的追踪关系；
6. 区分代码事实、来源方案事实、假设、偏差和仍需确认的事项；
7. 生成完整 executor-ready 内部方案；
8. 确认内部方案能回答：改哪些文件、改哪些函数、不能动什么、怎样算做完。

转换阶段不得：

- 修改代码、配置或测试；
- 改变 master 已确认的推荐方案；
- 用技术判断替代未确认的业务决策；
- 把无法确认的内容直接填成事实。

转换结果可以只保留在本次执行会话内部，也可以根据 master 指定或审计需要写入输入文件同目录的 `.execution.md` 文件。无论是否落盘，最终报告都必须说明转换结果和偏差。

遇到以下情况必须停在转换阶段：

- 方案状态未确认；
- 推荐方案不唯一或取舍未确认；
- 当前代码与方案冲突会改变目标、数据边界或业务行为；
- 必须修改非目标才能实现；
- 无法确定关键接口、状态、失败处理或回滚方式；
- 必须发明业务规则才能继续；
- 没有适用的精确 Role 索引。

### 3. 方案读取与角色预检

对最终执行的 executor-ready 方案，在建立执行清单或编辑任何文件前完成角色预检：

1. 完整读取方案及其来源决策方案（如果存在）。
2. 提取 `方案元信息`、`目标`、`需求范围`、`非目标`、`执行约束`、`阶段角色与职责`、`实现方案`、`修改范围`、`新增类与结构体设计`、`函数级修改设计`、`实现步骤`、`验收标准`、`代码静态校验`、`运行验证方式`、`风险与假设` 和 `最终交付要求`。
3. 从 `阶段角色与职责` 和 `实现步骤` 提取每个阶段的 Role 索引。
4. 确认角色索引来自 `Doc/AIPrompt/AIActor/README.md` 或其解析到的全局角色目录，且每个对应角色文档已完整阅读。
5. 确认两个章节中的阶段和 Role 索引一致，不存在遗漏、冲突或占位符。
6. 确认角色职责适合对应阶段，且没有把 TechStack、Domain、Requirement、Constraints 或 Acceptance 混入 Role。

以下任一情况出现时，立即停止，不得修改文件：

- 必要阶段没有 Role 索引；
- 索引不存在或对应角色文档缺失；
- 使用显示名称、临时名称或泛化身份代替 Role 索引；
- `阶段角色与职责` 和 `实现步骤` 的 Role 索引不一致；
- 角色文档无法覆盖方案分配的阶段职责；
- executor-ready 方案的来源状态或转换状态不符合要求。

### 4. 建立执行清单

将最终 executor-ready 方案转换成内部执行清单：

| 类别 | 必须提取的内容 |
| --- | --- |
| 允许操作 | 是否允许改代码、改配置、新增测试 |
| 禁止操作 | 非目标、执行约束、禁止触碰的模块 |
| 修改对象 | 文件或模块、修改类型、是否必须、修改目的 |
| 验收对象 | 每条验收标准及判断方式 |
| 验证对象 | 可运行验证、静态校验、人工验证、剩余风险 |
| 阶段角色 | 每个阶段的精确 Role 索引、对应角色文档、职责匹配结论、输出重点、切换条件 |

如果输入是人类方案，执行清单必须同时保留：

- 来源决策方案路径；
- 人工确认状态；
- 内部转换状态；
- 转换产生的代码事实、假设和偏差；
- 转换结果是否落盘。

### 5. 修改前核对

在编辑文件前完成：

1. 确认角色预检已经通过，并记录每个阶段采用的精确 Role 索引。
2. 阅读方案指定或推断的现有代码、配置、测试和文档。
3. 对照 `修改范围` 确认实际文件是否存在。
4. 确认关键接口、配置键、类名、方法名、topic、命令路径或 UI 绑定与方案一致。
5. 判断是否存在方案与代码冲突。
6. 如果需要修改方案外文件才能完成目标，先说明原因；只有必要依赖且不改变方案边界时才继续。

### 6. 执行修改

按方案的 `实现步骤` 分阶段修改：

- 进入每个阶段前，按方案记录的精确 Role 索引切换角色，并重新确认该角色文档的职责和边界。
- 先做最小必要改动。
- 保持现有架构、命名、异常处理、日志和配置风格。
- 只修改 `修改范围` 列出的文件、类型和函数。
- 不删除用户已有改动，不回滚无关文件。
- 如果执行中发现必须改变已确认业务决策、非目标或范围，立即停止并询问 master。

### 7. 运行验证

按方案的 `运行验证方式` 执行可运行的验证项，根据实际场景选择：

- 构建受影响项目；
- 运行聚焦单元测试或集成测试；
- 校验 JSON/XML 等配置语法；
- 启动服务或页面做手工验证；
- 设备/PLC/IO 场景使用模拟器、夹具、dry-run 或人工回归，不伪造真实设备验证结论。

如果验证失败，先判断是否由本次改动引入。能在方案范围内修复就修复后重跑；否则记录原因和剩余风险，不擅自扩展范围。

### 8. 代码静态校验

无论是否运行了测试，都必须执行方案中的 `代码静态校验`：

1. 逐条对照来源决策方案、执行方案元信息、需求范围、非目标、执行约束、实现步骤和验收标准。
2. 标出每项对应的代码位置，关键逻辑精确到类、方法或配置键。
3. 沿真实调用链检查数据流、状态流、接口调用、配置读取、错误处理和返回结果。
4. 检查字段名、参数名、配置键、事件名、topic、返回结构是否前后一致。
5. 检查是否遗漏错误处理、空状态、权限、重复提交、并发、回滚、重启或兼容性处理。
6. 检查条件写反、默认值错误、状态未更新、异常被吞掉、资源未释放等明显逻辑错误。
7. 检查是否引入方案之外的重构、格式化、无关文件修改或行为变化。
8. 列出无法静态确认、必须实际运行或联机验证才能确认的风险。
9. 给出结论：可以进入下一步 / 需要修改 / 必须运行验证后再判断。

### 9. 最终交付

最终回复必须按执行方案的 `最终交付要求` 输出。至少包含：

- 修改文件列表；
- 实际新增类型及最终声明；
- 实际修改和新增函数及最终签名；
- 每个文件、类型和函数的变更摘要；
- 每条验收标准的完成情况；
- 来源决策方案目标、非目标和不变量是否保持；
- 执行约束遵守情况；
- 转换阶段摘要（若本次输入是人类方案）；
- 本次 subagent 执行模型、Agent 名称和状态；
- 阶段 Role 索引和角色边界遵守情况；
- 实际运行的测试或验证命令及结果；
- 静态校验报告；
- 无法验证的原因；
- 剩余风险和人工检查项。

## 阻塞处理

以下情况应先暂停并向 master 说明，不要硬执行：

- 人类方案仍为 `待人工确认`；
- master 没有明确授权已确认的人类方案进入执行；
- 推荐方案不明确或关键业务取舍未确认；
- 内部转换无法生成完整 executor-ready 方案；
- 方案要求与现有代码结构明显冲突，继续执行会改变目标或扩大范围；
- 必须修改方案明确列为非目标的内容；
- 需要访问工作区外文件、网络、生产服务或硬件资源，但当前权限不可用；
- 方案缺少必要的 `plan-executor` Agent、可用模型或中止能力；
- 角色索引缺失、不存在、不匹配或仍是占位符；
- 需要通过重新设计、改变推荐方案或补充未确认业务规则才能继续；
- executor-ready 输入的来源方案状态不是 `已确认`，或转换状态不是 `已转换`。

## 最终检查

结束前确认：

- 已完整读取输入方案；
- 已正确识别输入是人类方案还是 executor-ready 方案；
- 人类方案输入已在 executor 内部完成转换，master 不需要手动调用 `$ai-plan-converter`；
- 已确认人工方案状态，且没有被绕过的业务决策闸门；
- executor-ready 方案的来源状态为 `已确认`、转换状态为 `已转换`；
- 已完成角色预检，并完整阅读所选角色文档；
- 没有自行创造、近似替代、默认补充或静默更换角色；
- 没有改变已确认的目标、推荐方案、非目标和业务取舍；
- 没有违反执行约束，也没有方案外重构或无关文件修改；
- 已完成静态校验并真实报告运行验证结果；
- 未验证内容已明确列为剩余风险；
- 已按方案的最终交付要求完成报告。
