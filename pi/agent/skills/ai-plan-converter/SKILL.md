# AI 方案转换器

## 目标

把已经由 master 判断并确认的面向人类方案，转换为可由 `$ai-plan-executor` 严格执行的 executor-ready 源码实施方案。

```text
面向人类的决策方案
    ↓
读取并核对当前代码、配置、测试和项目规则
    ↓
executor-ready 实施方案
```

本 skill 是独立的方案转换能力，不实现代码，不运行实现，不替 master 重新做业务决策。它可以由 master 作为可选的执行前预审入口单独调用，也可以由 `$ai-plan-executor` 在同一执行会话内部自动使用；master 不需要为默认执行路径手动调用本 skill。

## 三阶段工作流中的位置

```text
$ai-plan-doc-writer
    ↓
人工判断和确认
    ↓
$ai-plan-executor（内部自动使用本转换能力）
    ↓
面向 AI 的 executor-ready 方案
    ↓
执行、验证和交付
```

master 可以把已确认的人类方案直接交给 `$ai-plan-executor`。单独调用 `$ai-plan-converter` 只用于希望在代码修改前审查 executor-ready 细节的场景。不得绕过人工确认把人类方案直接执行。

## 调用与范围边界

- 仅在用户明确调用 `$ai-plan-converter`、明确要求把已确认方案转换为执行方案，或由 `$ai-plan-executor` 在内部编排调用时运行。
- 输入必须是面向人类的决策方案 Markdown，并且人工确认状态为 `已确认`，或 master 在当前请求中明确确认该方案可以转换。
- 如果方案仍为 `待人工确认`、包含阻塞性待确认事项、推荐结论不明确或关键业务取舍未确认，停止并说明阻塞点。
- 本 skill 可以读取当前项目代码、配置、测试和文档，以确定真实实现范围；不得修改这些文件。
- 本 skill 只生成执行方案，不执行方案，不启动实现 subagent；即使由 `$ai-plan-executor` 在内部使用，转换完成后也必须将控制权交回 executor，不能在转换阶段开始修改代码。
- 不得静默改变人类方案的目标、推荐结论、非目标或业务取舍。发现冲突时停下并要求 master 决定。

## 输入要求

### 必须读取

1. 用户指定的已确认人类决策方案。
2. 项目规则和 `AGENTS.md`。
3. 六要素指南，按以下顺序取第一份存在的文件：
   - `{project}/Doc/AIPrompt/AI提示词六要素设计指南.md`
   - `C:\Users\41290\.pi\agent\Domain\AIUse\AI提示词六要素设计指南.md`
4. 角色目录，按以下顺序取第一份存在的文件：
   - `{project}/Doc/AIPrompt/AIActor/README.md`
   - `C:\Users\41290\.pi\agent\Actor\README.md`
5. 执行方案模板：
   - `C:\Users\41290\.pi\agent\skills\ai-plan-doc-writer\源码修改执行方案模板.md`
   - 如仓库已有同步副本，核对两份模板是否一致。
6. 人类方案中涉及的当前代码、配置、测试和文档。

### 人工确认门槛

转换前必须确认：

- `方案状态` 为 `已确认`，或 master 明确表示可以转换；
- `推荐方案` 唯一且清楚；
- `目标`、`非目标`、`约束与不变量` 没有互相冲突；
- 影响实现范围的 `待确认事项` 已解决；
- 仍然未知的内容被标记为假设或待验证，不得伪装成事实。

## 转换原则

### 保留决策，不偷换方案

转换器负责将“为什么”和“做什么”落到代码结构，不负责重新选择业务方案：

| 人类方案信息 | 执行方案落点 |
| --- | --- |
| 问题定义和目标 | `目标`、`需求范围` |
| 背景中的对象、流程、状态 | `背景与现状`、`实现方案` |
| 非目标和约束 | `非目标`、`执行约束` |
| 推荐方案的行为路径 | `实现方案`、`实现步骤` |
| 方案风险和失败方向 | `验收标准`、`运行验证方式`、`风险与假设` |
| 人工判断结论 | 转换前提和来源追踪，不替代代码验收 |

每一项重要需求都应能追踪到：

```text
决策方案条目
    → 执行方案需求/步骤
    → 修改文件、类型或函数
    → 验收标准和验证证据
```

### 事实优先

- 代码、配置、测试和项目规则优先于人类方案中对现状的猜测。
- 如果代码事实与方案描述冲突，记录具体冲突并停止；不能自行选择一边继续。
- 如果只是文件路径或函数签名与方案中的预估不同，但不改变目标和边界，可以在执行方案中采用真实路径，并记录偏差。
- 不确定的业务规则必须保留为待确认事项，不能由转换器发明。

### 执行化补齐

转换器必须补齐 executor 需要的内容：

- 准确的文件或模块范围；
- 相关类型和函数；
- 数据流、状态流、主路径和失败路径；
- 允许修改和禁止修改的范围；
- 不变量、兼容性和回滚要求；
- 分阶段实现步骤；
- true/false 验收标准；
- 代码静态校验要求；
- 适合当前仓库和改动的运行验证方式；
- 风险、假设和无法确认的事项。

不要把最终生产代码写入执行方案，只写框架级伪代码。

## 角色与职责

转换阶段至少需要覆盖两类判断：

- `architect`：确认人类方案的边界、数据所有权、失败半径、结构取舍和不能偷换的决策。
- `developer`：根据当前代码定位真实文件、类型、函数和最小改动路径。

生成的 executor-ready 方案必须按已解析角色目录的精确 Role 索引填写 `阶段角色与职责`。如果角色目录中缺少适合某个阶段的索引，停止，不创造或近似替代角色。

## 工作流程

1. 读取人类方案完整内容，检查人工确认状态和阻塞问题。
2. 读取项目规则、六要素指南、角色目录和执行模板。
3. 先以 `architect` 视角核对推荐方案、边界、失败方式和不变量是否能被当前实现承载；发现业务决策冲突时停止。
4. 以 `developer` 视角阅读当前代码、配置、测试和调用方，确定真实文件、类型、函数、接口和验证入口。
5. 对照人类方案逐项建立追踪关系，区分已确认事实、代码事实、假设、偏差和待确认事项。
6. 按执行模板生成 executor-ready 方案。保留模板的章节顺序和标题，不改成架构论文。
7. 在 `方案元信息` 中写明：
   - `来源决策方案`：输入文档路径；
   - `来源方案状态`：`已确认`；
   - `转换状态`：`已转换`；
   - `转换说明`：记录代码事实核对结果和必要的局部路径偏差。
8. 将每个需求、非目标、约束和验收标准写成可追踪、可执行的条目。
9. 检查 executor 能回答四个问题：改哪些文件、改哪些函数、不能动什么、怎样算做完。
10. 将转换后的方案写入新文件。默认使用输入文件名加 `.execution.md`，除非 master 指定输出路径。
11. 停止并交付转换结果，不修改代码，不启动执行器；如果由 `$ai-plan-executor` 在内部使用，则将转换结果交回 executor，由 executor 继续执行或在阻塞时停止。

## 生成方案的硬性要求

转换后的方案必须保留模板要求的：

- `目标`
- `背景与现状`
- `需求范围`
- `非目标`
- `执行约束`
- `阶段角色与职责`
- `实现方案`
- `修改范围`
- `新增类与结构体设计`
- `函数级修改设计`
- `实现步骤`
- `验收标准`
- `代码静态校验`
- `运行验证方式`
- `风险与假设`
- `最终交付要求`
- `执行入口提示`

其中：

- `修改范围` 不得为空；每个文件写明修改类型、涉及类型、函数和修改目的。
- `函数级修改设计` 不得为空；现有函数使用真实签名，新函数使用明确标记为建议的签名。
- 无新增类型时必须写 `无新增类或结构体`。
- 伪代码只能表达校验、分支、调用、状态变化、错误处理和返回行为。
- 验收标准必须可以标记为 `已满足`、`未满足` 或 `部分满足`。
- `运行验证方式` 必须针对实际仓库和改动，不得写泛化的“运行测试”。
- 执行入口必须指向 `$ai-plan-executor`，而不是 `$ai-plan-converter`。

## 阻塞条件

以下情况必须停止，不生成可执行方案：

- 人工确认状态不是 `已确认`，且 master 没有明确授权转换；
- 推荐方案不明确，或存在未解决的业务取舍；
- 当前代码与推荐方案存在会改变目标、边界或数据所有权的冲突；
- 必须修改人类方案列出的非目标才能实现；
- 无法确定关键文件、接口、状态或失败处理，且无法通过代码阅读确认；
- 角色目录没有覆盖必要阶段的精确 Role 索引；
- 执行模板缺少必要章节，或模板同步副本存在未解释差异。

可以局部处理但必须记录的情况：

- 方案只给出模块级范围，而代码阅读可以安全定位到具体文件；
- 方案中的文件路径或函数签名是预估值，但代码能确认真实值；
- 运行环境不可用，但可以写出明确的未来验证步骤。

## 完成检查

交付前确认：

- [ ] 来源人类方案已明确人工确认。
- [ ] 未改变推荐方案、目标、非目标和业务取舍。
- [ ] 已阅读当前代码并区分代码事实、假设和偏差。
- [ ] 每个需求都能追踪到实现步骤、修改对象和验收标准。
- [ ] 修改范围和函数级设计均非空且可执行。
- [ ] 不新增方案外抽象，不写最终生产代码。
- [ ] 执行方案包含静态校验、运行验证、风险和最终交付要求。
- [ ] `方案元信息` 含来源路径、来源状态和 `转换状态：已转换`。
- [ ] 生成文档可以交给 `$ai-plan-executor` 执行；默认路径允许 executor 内部先完成转换后再执行。
- [ ] 人类方案未确认时，无论是单独调用还是内部使用，都不能生成可执行结果。
