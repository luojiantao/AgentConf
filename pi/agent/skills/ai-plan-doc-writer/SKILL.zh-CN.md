# AI 方案决策文档写作者

## 目标

生成一份首先服务于人类判断的方案决策文档。读者应能在不阅读代码实现细节的前提下回答：

- 要解决的问题是否真实且值得解决？
- 目标和非目标是否清楚？
- 推荐方案是否比替代方案合理？
- 主要取舍、失败方式和风险是否可以接受？
- 是否可以确认方案并进入转换阶段？

本 skill 不生成 executor-ready 方案，不直接执行方案，不修改代码、配置或测试。人工确认后，master 可以把本 skill 生成的方案直接交给 `$ai-plan-executor`；executor 会在内部完成执行化转换。

## 三阶段工作流

```text
$ai-plan-doc-writer
    ↓
面向人类的方案决策文档
    ↓
人工判断和确认
    ↓
$ai-plan-executor（对外统一入口）
    ├─ 内部自动转换为 executor-ready 方案
    └─ 内部自动执行、验证和交付
```

`ai-plan-doc-writer` 的输出在人工确认前不能执行；人工确认后可以直接交给 `$ai-plan-executor`。`$ai-plan-converter` 是可选的独立审查入口，不是 master 必须手动调用的步骤。

## 调用与范围边界

- 仅在用户明确调用 `$ai-plan-doc-writer` 时运行；普通的“写方案”“分析方案”“讨论做法”不隐式触发本 skill。
- 适用于后续可能需要代码实现的功能、缺陷修复、重构、UI/服务调整或跨模块变更的方案决策。
- 也可以先用于需要结构判断的代码相关架构方案；如果最终不涉及代码修改，不应继续使用 `$ai-plan-executor`。
- 本 skill 只写决策文档，不实现、不测试、不修改任何项目代码、配置或测试状态。
- 不要把最终生产代码、函数级实施步骤、可直接执行的命令或 executor 角色阶段表写入决策文档。

## 资料边界

按以下顺序解析六要素指南，使用第一份存在的文件：

1. `{project}/Doc/AIPrompt/AI提示词六要素设计指南.md`
2. `C:\Users\41290\.pi\agent\Domain\AIUse\AI提示词六要素设计指南.md`

遵守：

```text
Prompt = Role + TechStack + Domain + Requirement + Constraints + Acceptance
```

决策文档中的信息分层：

| 要素 | 决策文档位置 |
| --- | --- |
| Role | `决策视角`，只说明负责判断的角色和边界 |
| TechStack | `背景与现状` 或 `约束与不变量` 中的已确认技术事实 |
| Domain | `背景与现状` 中的对象、流程、状态和业务规则 |
| Requirement | `问题定义` + `目标` |
| Constraints | `非目标` + `约束与不变量` |
| Acceptance | `人工判断标准`，描述方案是否值得确认，不伪造代码已完成 |

角色只表示判断视角，不得把本次需求、技术版本、业务名词或验收结论写进角色定义。

## 角色选择

1. 先读取角色目录：优先 `{project}/Doc/AIPrompt/AIActor/README.md`，否则读取 `C:\Users\41290\.pi\agent\Actor\README.md`。
2. 完整阅读候选角色文档，再选择与当前决策最匹配的精确 Role 索引。
3. 结构和边界决策通常使用 `architect`；界面路径使用 `interface`；玩法使用 `game-designer`。如果没有适合的索引角色，停止并说明角色缺口，不自行创造角色。
4. 决策文档只记录一个主要决策视角和必要协作视角，不生成执行阶段角色表。执行阶段角色由转换后的 executor-ready 方案单独定义。

## 工作流程

1. 确认用户明确调用了本 skill，并确认任务存在需要判断的方案目标。
2. 读取六要素指南和角色目录，选择决策视角。
3. 对代码相关任务阅读必要的现有代码、配置、测试和文档；只记录已确认事实，不把推测写成事实。
4. 明确问题、目标、非目标、约束、不变量和待确认事项。
5. 至少给出两个可行选项，其中必须包含“保持更简单的现状/少拆一层”作为对照，除非有明确理由不适用。
6. 用目标价值、复杂度、失败半径、耦合、兼容性、验证成本和演进能力比较方案。
7. 给出推荐方案、推荐理由、放弃的取舍、失败处理方向和演进信号。
8. 使用 `人类方案决策模板.md` 写出方案，初始状态必须为 `待人工确认`。
9. 写入文档后停止，不修改实现代码；人工确认后，master 可以直接调用 `$ai-plan-executor`，不需要手动调用 `$ai-plan-converter`。

## 决策文档要求

### 首屏必须能回答

- 这份方案要解决什么问题？
- 推荐做什么？
- 为什么推荐？
- 需要 master 确认什么？
- 确认后是否可以直接进入 `$ai-plan-executor`？

### 必须区分

- **已确认事实**：有代码、配置、测试、日志或用户说明依据。
- **判断**：对目标、方案和取舍的明确结论。
- **假设**：尚未验证、转换阶段需要核对的内容。
- **待确认事项**：不确认就不能安全进入转换阶段的内容。

### 必须包含

- 一句话问题定义和做错的判定。
- 背景与现状，包括相关对象、状态、不变量和影响范围。
- 目标与非目标。
- 约束和不可破坏的行为。
- 至少两个候选方案及其优缺点。
- 推荐方案及推荐理由。
- 主路径、失败路径和用户/调用方可观察到的结果。
- 风险、回滚方向和复杂化的演进信号。
- 人类判断标准和待确认事项。
- 人工确认状态，以及确认后直接转入 `$ai-plan-executor` 的说明；如需审查执行细节，再说明可选的 `$ai-plan-converter` 路径。

### 不应包含

- 精确的文件修改表、函数修改表或新增类骨架。
- 以“修改某函数、增加某方法”为核心的执行步骤。
- 可直接复制运行的实现代码或最终生产代码。
- `ai-plan-executor` 的执行阶段细节、静态校验报告模板或运行命令清单。
- 未经确认的技术选型、业务规则、文件路径或性能指标。

## 方案比较规则

每个候选方案至少说明：

- 解决的具体问题；
- 主要路径和行为变化；
- 对现有数据、边界或用户的影响；
- 复杂度和认知负担；
- 失败半径和恢复方式；
- 兼容性和验证成本；
- 何时需要进一步演进。

推荐方案必须回答“为什么现在选择它”，不能只写“最佳实践”或“更灵活”。如果约束未知，标记为未知，不自行补全。

## 人工确认协议

生成文档时：

- `方案状态` 必须写 `待人工确认`。
- 不得把 AI 自己的推荐当作 master 已确认的决定。
- 待确认事项为空时，也必须保留人工确认记录，并由 master 明确确认。
- master 确认后，应将文档状态改为 `已确认`，或在确认消息中明确指定该文档可以执行。
- 只有状态为 `已确认` 且没有阻塞性待确认事项时，才允许交给 `$ai-plan-executor`。
- 如果 master 想在执行前审查文件和函数级落地细节，可以额外调用 `$ai-plan-converter`；这不是默认必经步骤。
