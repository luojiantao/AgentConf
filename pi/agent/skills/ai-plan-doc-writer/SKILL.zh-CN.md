# AI 方案落地文档写作

## 目标

创建一份可以让另一个 AI agent 安全、机械化执行的 Markdown 代码修改方案。文档必须说明要修改什么代码、为什么修改、改哪里、怎么实现、每个执行阶段使用什么角色、哪些不做、如何判断完成、如何执行强制代码静态校验，以及还剩哪些风险。

遵循六要素边界。按以下顺序解析指南，使用第一份存在的文件：

1. `{project}/Doc/AIPrompt/AI提示词六要素设计指南.md`
2. `C:\Users\41290\.pi\agent\Domain\AIUse\AI提示词六要素设计指南.md`

```text
Role + TechStack + Domain + Requirement + Constraints + Acceptance
```

`Role` 只描述身份、职责、判断视角、工作方式和职责边界。不得把技术栈、业务知识、当前需求、执行约束或验收标准混入角色说明。

六要素必须拆到对应章节，禁止写进同一节：

| 六要素 | 落到方案哪一节 |
| --- | --- |
| Role | `阶段角色与职责`，以及每个实现步骤开头的当前角色 |
| TechStack | `执行约束` 里的工程规范，不写进角色 |
| Domain | `背景与现状` 里的对象、状态、不变量 |
| Requirement | `目标` + `需求范围` |
| Constraints | `非目标` + `执行约束` |
| Acceptance | `验收标准` + `代码静态校验` + `运行验证方式` |

这个 skill 面向两段式工作流：

```text
ai-plan-doc-writer -> 可执行方案 MD -> ai-plan-executor
```

本 skill 只负责编写方案，不执行方案，也不要把代码实现工作混入方案编写阶段。

## 权威模板

必须按本 skill 的模板填成可执行方案，不得另起论文式或自创目录：

- skill 内权威副本：`C:\Users\41290\.pi\agent\skills\ai-plan-doc-writer\源码修改执行方案模板.md`
- Domain 同步副本：`C:\Users\41290\.pi\agent\Domain\AIUse\源码修改执行方案模板.md`

规则：

- 写方案前先完整阅读该模板。
- 章节顺序和标题必须与模板一致。
- 禁止改成 IMRaD / 文献综述 / 学术贡献 / 纯架构说明。
- 不要把模板开头的「适用 / 不适用」「填写规则」抄进生成方案。从方案标题开始。
- 填完后执行者必须能判断四件事：改哪些文件、改哪些函数、不能动什么、怎样算做完。
- `修改范围` 或 `函数级修改设计` 空着，方案还不能交付。必须先读现有代码。
- 不要把最终生产代码写进方案，只写框架级伪代码。
- 小修可以缩短叙述，但不可删除：`目标`、`需求范围`、`非目标`、`执行约束`、`修改范围`、`函数级修改设计`、`验收标准`、`代码静态校验`、`运行验证方式`。
- 无新增类型时，保留 `新增类与结构体设计` 并写 `无新增类或结构体`。

## 调用与范围边界

- 仅当用户明确调用 `$ai-plan-doc-writer` 时运行本 skill。
- 不得因用户普通地提出“写方案”“分析问题”“讨论做法”或“编写文档”而隐式触发。
- 仅用于生成执行后会修改源代码的实施方案。
- 关联配置、测试和文档只有在它们是代码修改不可缺少的组成部分时，才能纳入方案。
- 架构方案、纯配置方案、纯文档方案、纯排查方案、运维流程、工作流设计、不涉及代码改动的测试方案及其他非代码方案不得使用本 skill。
- 如果用户明确调用了本 skill，但目标任务不需要修改源代码，必须停止并说明该任务不在本 skill 范围内，不得继续使用本 skill 生成方案。

## 工作流程

1. 确认用户已经明确调用 `$ai-plan-doc-writer`，并确认目标需要修改源代码：功能代码开发、缺陷修复、代码重构、UI 或服务代码改动、测试代码改动，或代码改动必需的关联配置调整。任一条件不满足时停止。
2. 阅读已解析的六要素指南，保持 Role、TechStack、Domain、Requirement、Constraints 和 Acceptance 的边界。
3. 按以下顺序解析角色目录，使用第一份存在的文件：
   - `{project}/Doc/AIPrompt/AIActor/README.md`
   - `C:\Users\41290\.pi\agent\Actor\README.md`
   选择前完整阅读每个候选角色文档。已解析目录是 Role 索引的唯一来源。
4. 阅读本 skill 目录中的 `源码修改执行方案模板.md`。生成方案必须使用该模板的标题、表格和章节顺序。
5. 为每个执行阶段匹配已解析目录中的现有角色索引。先用模板默认表（`developer` + `code-requirement-verifier`），但必须先确认这些索引存在。任何必要阶段没有合适角色，或默认索引不存在时，必须在创建或修改方案文档前停止，并询问用户是新增角色还是指定现有角色；禁止自行创造、近似替代或静默降级。
6. 编写最终方案前，先阅读相关本地代码、配置、文档或已有方案。如果暂时无法确定精确文件，也要检查仓库到足以列出可能模块和必要发现步骤。
7. 判断方案类型、风险等级、允许的操作类型、影响范围、重启需求和推荐执行 skill。
8. 区分必须实现的范围、非目标和硬性执行约束。
9. 根据实际场景描述实现路径，包括数据流、状态流、API 调用、服务交互、配置变更、UI 行为、持久化变化或文档变化。
10. 用结构化列列出每个预计修改的源文件：修改类型、是否必须、修改目的、涉及类型和涉及函数。
11. 编写新增类型设计，列出每个需要新增的类或结构体，解释新增原因，并给出命名空间、声明、职责、依赖、状态、公开成员、生命周期和框架级类型骨架。
12. 编写函数级修改设计，区分需要修改的现有函数和需要新增的函数。为每个关键函数提供框架级伪代码，描述校验、分支、调用、状态变化、错误处理和返回行为，但不写最终实现。
13. 把选定的角色索引局部绑定到执行阶段。角色只在当前阶段生效，不是整个对话的全局身份。
14. 将实现步骤拆成阶段：代码阅读、修改前确认、实现、自检、运行验证、静态校验、最终交付。
15. 将验收标准写成可以判断真假的检查项。
16. 必须包含 `代码静态校验` 章节，并使用下方固定校验方式。
17. 根据实际任务编写 `运行验证方式`。不要套用不适合当前仓库或当前改动的通用命令。
18. 以风险、假设、最终交付要求和 `$ai-plan-executor` 执行入口提示收尾。
19. 交付的是填好的模板，不是论文。完成前确认四件执行问题都已回答，且没有加入 IMRaD、文献综述或学术贡献章节。

## 章节规则

### 方案元信息

将本章节放在文档前部，方便 executor 快速选择执行策略。

使用表格：

```md
| 项目 | 内容 |
| --- | --- |
| 方案类型 | 功能代码开发 / 缺陷修复 / 代码重构 / UI 代码调整 / 服务代码改动 / 测试代码改动 |
| 风险等级 | 低 / 中 / 高 |
| 主要影响范围 | `path/or/module` |
| 是否允许改代码 | 是 / 否 |
| 是否允许改配置 | 是 / 否 |
| 是否允许新增测试 | 是 / 否 |
| 是否需要重启服务 | 是 / 否 / 待确认 |
| 推荐执行 skill | `ai-plan-executor` |
| 角色策略 | 仅使用已解析角色目录中的 Role 索引，按 `阶段角色与职责` 逐阶段切换 |
```

根据任务上下文选择具体值。只有代码阅读后仍无法判断时才写 `待确认`。

### 目标

说明最终可观察到的结果。避免只写“优化”“完善”“支持”这类模糊词，除非后面紧跟明确行为。

### 背景与现状

说明当前行为、已有能力、当前限制以及为什么需要本次改动。尽量引用已知类名、模块、配置文件、命令、页面、服务或工作流。

### 需求范围

只列出本次必须实现的内容。每一项都应是可执行的。

### 非目标

列出本次不应该修改的内容。用这个章节限制大范围重构、无关 UI 重设计、权限变更、数据迁移、协议变更或需求外行为变化。

### 执行约束

为 executor 写硬规则。可包含：

```md
- 必须严格按本文档范围执行。
- 不允许进行方案外重构、统一格式化或无关清理。
- 不允许修改未列入修改范围的业务逻辑，除非实现步骤明确要求。
- 如果发现方案与现有代码冲突，必须先停止并说明冲突，不得自行扩大范围。
- 如果实际代码结构与方案预估文件不一致，必须先补充实际文件清单，再继续实现。
- 涉及配置、设备动作、数据库或调度逻辑时，必须保留回滚和人工验证说明。
- 技术与工程规范以当前仓库及对应 Stack 文档为准，不在角色定义里重复。
```

根据方案调整约束。不要把约束写得过宽，导致执行无法推进。

### 阶段角色与职责

当方案包含多个执行阶段，或同一对话中需要切换不同视角时，必须写本章节。角色必须明确、务实，并且只绑定到对应阶段。

编写本章节前，必须执行以下角色选择流程：

1. 将已解析角色目录作为可用角色的唯一事实来源：优先 `{project}/Doc/AIPrompt/AIActor/README.md`，否则 `C:\Users\41290\.pi\agent\Actor\README.md`。
2. 使用目录中的精确 Role 索引，例如 `architect`、`developer`、`code-requirement-verifier`，或项目索引如 `bionanosemi-dev`；不得用临时创造的显示名称替代索引。
3. 完整阅读每个候选索引链接的 Markdown 文档，确认其身份、核心职责、判断视角、工作方式和职责边界适合当前阶段。
4. 同一角色的既有职责能覆盖多个阶段时，可以复用同一个 Role 索引；不得为了让每个阶段名称不同而创造额外角色。
5. 先套用模板默认表。若已解析目录中没有 `developer` 或 `code-requirement-verifier`，必须停止并询问，不得静默换成别的角色。
6. 必要阶段没有任何索引角色满足时，必须停止并询问用户；不得继续编写方案、使用目录外的兜底角色或扩大现有角色职责。
7. 用户指定的角色不在索引中时，必须询问用户是将其添加到已解析角色目录，还是改选现有索引。

使用模板默认表。先核对每个索引确实存在，再按角色文档改写该行职责：

```md
| 阶段 | Role 索引 | 本阶段职责 | 输出重点 | 切换条件 |
| --- | --- | --- | --- | --- |
| 代码阅读阶段 | `developer` | 核对真实文件、调用链、冲突点 | 文件清单、调用链 | 关键代码和配置已定位 |
| 修改前确认阶段 | `developer` | 核对范围、非目标、约束仍成立 | 冲突与待确认项 | 无未决冲突，或已请示用户 |
| 实现阶段 | `developer` | 按修改范围做最小改动 | 代码变更 | 代码改动完成 |
| 自检阶段 | `developer` | 对照验收标准和执行约束 | 自检表 | 自检完成 |
| 运行验证阶段 | `developer` | 执行本文指定的命令或操作 | 验证记录 | 能跑的项已跑完 |
| 静态校验阶段 | `code-requirement-verifier` | 用代码证据核对需求完成度，不改代码 | 校验报告 | 结论明确 |
| 最终交付阶段 | `developer` | 按最终交付要求汇总 | 交付清单 | 文档齐全 |
```

若某阶段需要结构判断、界面路径或玩法验收，再把该行换成 `architect` / `interface` / `playtester` 等现有索引，并改写职责。最终方案不得保留占位符。

规则：

- 不要只在文档开头放一个全局角色并让全流程沿用。
- executor 只在进入对应阶段时切换到该阶段角色。
- 每个角色必须说明关注点和应该输出的内容。
- 角色说明不能覆盖 `需求范围`、`非目标`、`执行约束`、安全要求或用户指令。
- 方案中记录的角色名称必须是 Role 索引；可在职责文字中补充可读身份，但不得用显示名称替代索引。
- 本阶段职责必须来自选定角色文档，并遵守六要素指南定义的 Role 边界。
- 不得使用默认或兜底角色，除非该角色索引确实存在于角色目录，且正文职责能够覆盖当前阶段。

### 实现方案

描述核心实现思路。按实际场景覆盖相关流程：

- 前端/UI：用户操作、ViewModel 或状态更新、命令绑定、loading/error/success 状态、展示刷新。
- 后端/服务：请求入口、参数校验、业务逻辑、持久化、错误处理、返回结构。
- 分布式设备控制：调用方、服务/模块、命令路径、DataSync topic、Job 状态、IO/配置依赖、重启行为。
- 配置：文件路径、键名、默认值、兼容性、热加载或重启行为。
- 数据库/存储：schema 或字段映射、迁移或兼容策略、回滚。

只有当流程存在分支、跨服务调用或状态转换，不画图会产生歧义时，才使用 Mermaid。

### 修改范围

使用结构化表格：

```md
| 文件或模块 | 修改类型 | 是否必须 | 涉及类/类型 | 涉及函数 | 修改目的 |
| --- | --- | --- | --- | --- | --- |
| `path/to/file` | 修改 / 新增 / 删除 / 待确认 | 必须 / 可选 | `TypeName` | `ExistingMethod`、`NewMethod`（新增） | 说明为什么要改 |
```

应根据当前代码检查结果尽量列出精确源文件。每个源文件必须写明涉及的类/类型和函数。如果文件只修改项目元数据、using/import、类型声明、字段、属性、XAML、生成代码或配置，不涉及函数，则写 `不涉及函数`，并说明具体修改的符号或章节。如果暂时不知道精确路径，写模块路径，并在实现步骤中要求 executor 编辑前定位精确文件。

### 新增类与结构体设计

每份方案都必须写本章节。没有新增类或结构体时，必须明确写 `无新增类或结构体`；否则先列出全部新增类型：

```md
| 文件 | 命名空间 | 类型名称 | 类型种类 | 可见性 | 基类/接口 | 核心职责 | 新增原因 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `path/to/NewType.cs` | `Project.Namespace` | `NewType` | class / struct | public / internal | `BaseType`、`IContract` / 无 | 单一职责 | 为什么不能复用现有类型 |
```

每个新增类或结构体必须满足：

- 解释职责边界、调用方/使用方、依赖、持有状态；相关时说明线程安全和生命周期要求，以及为何新建类型比扩展现有类型更合适。
- 给出建议声明，包括命名空间、可见性、`class` 或 `struct`、基类、实现接口，以及 `sealed`、`abstract`、`readonly` 等重要修饰符。
- 列出重要字段、属性、构造依赖、公开函数和私有辅助函数；其中每个可调用成员还必须出现在 `函数级修改设计`。
- 提供不可编译的框架级类型骨架，只表达结构和关系，不写生产函数体，不虚构未经代码验证的仓库 API。
- 每个新增类型都必须映射到 `修改范围` 中的文件，不得只列新增文件而不解释其中的类型。

使用以下格式：

````md
#### `path/to/NewType.cs` — `Namespace.NewType`

- 类型：class / struct
- 职责：说明单一职责和边界
- 使用方：说明谁创建、持有或调用它
- 生命周期：singleton / scoped / transient / value object / 手工管理
- 新增原因：解释为什么需要新类型

```text
type NewType : BaseType, IContract
    dependencies:
        verified dependency contracts
    state:
        fields and properties with ownership notes
    construction:
        constructor inputs and invariants
    public surface:
        methods and their responsibilities
    private helpers:
        helper names and boundaries
```
````

### 函数级修改设计

每份方案都必须写本章节。先使用结构化表格：

```md
| 文件 | 类/类型 | 函数或成员 | 变更类型 | 建议签名 | 职责 | 调用关系 |
| --- | --- | --- | --- | --- | --- | --- |
| `path/to/file` | `TypeName` | `ExistingMethod` | 修改现有函数 | `ReturnType ExistingMethod(Args)` | 修改后的职责 | 由谁调用、调用谁 |
| `path/to/file` | `TypeName` | `NewMethod` | 新增函数 | `ReturnType NewMethod(Args)` | 新函数职责 | 由谁调用、调用谁 |
```

规则：

- 列出函数体、签名、可见性、特性或调用契约会发生变化的每个现有函数。
- 列出每个需要新增的函数、构造函数、事件处理器、命令处理器、测试函数或其他可调用成员。
- 现有函数使用当前真实签名；新增函数应按现有代码风格提出建议签名，无法确认的细节必须明确标记。
- 重载函数必须用完整签名区分；每个函数都必须写明所属类/类型。
- 每个函数条目必须映射到 `修改范围` 中的文件，不得出现孤立的函数设计。
- 表格后必须为每个关键修改函数或新增函数提供框架级伪代码。伪代码按需覆盖控制流、输入校验、重要分支、调用、状态修改、异常/错误处理和返回行为。
- 伪代码使用语言无关或类似 C# 的非编译形式，不得写成最终生产实现，不展开既有样板代码，也不得虚构未经代码验证的仓库 API。
- 行为完全一致的简单访问器可以合并描述，但它们的名称仍必须出现在表格中。

每个函数使用以下格式：

````md
#### `path/to/file` — `TypeName.MethodName`

- 变更类型：修改现有函数 / 新增函数
- 目标：说明函数修改后的单一职责

```text
function MethodName(arguments):
    validate required inputs
    if guard condition fails:
        record or return the defined failure result
    call verified dependency
    update required state
    return result
```
````

### 完整案例

以下精简案例只说明必须采用的格式，路径和符号均为示意，不代表仓库事实。

````md
## 修改范围
| 文件 | 类型/成员 | 变更 | 说明 |
| --- | --- | --- | --- |
| `ProcessJobStateHandler.cs` | `ProcessJobStateHandler.HandleAsync` | 修改函数 | 在状态推进前调用幂等组件 |
| `ProcessJobMessageDeduplicator.cs` | `ProcessJobMessageDeduplicator` | 新增类 | 封装消息处理权声明 |
| `ProcessJobMessageKey.cs` | `ProcessJobMessageKey` | 新增结构体 | 表达不可变幂等键 |

## 新增类与结构体设计
- `internal sealed class ProcessJobMessageDeduplicator`：持有已验证的幂等存储依赖；由处理器调用；新增原因是隔离存储细节。
- `internal readonly struct ProcessJobMessageKey`：持有 PJ 与消息标识；不持有服务或可变状态；新增原因是约束幂等键。
```text
class ProcessJobMessageDeduplicator:
    dependency: verified idempotency store
    public: TryAcquireAsync(ProcessJobMessageKey key)
readonly struct ProcessJobMessageKey:
    immutable state: processJobId, messageId
    construction: validate and assign identifiers
```

## 函数级修改设计
| 函数 | 变更 | 职责 |
| --- | --- | --- |
| `ProcessJobStateHandler.HandleAsync` | 修改 | 校验、查重后沿原路径推进状态 |
| `ProcessJobMessageDeduplicator.TryAcquireAsync` | 新增 | 原子声明消息处理权 |
```text
HandleAsync(message):
    validate identifiers
    if await deduplicator.TryAcquireAsync(key) is false: log and return
    call existing state advancement path
````

### 实现步骤

按阶段组织：

```md
### 1. 代码阅读阶段

当前 Role：`developer`

- 阅读 `修改范围` 中的文件和调用方。
- 确认真实签名、错误处理、配置键与方案是否一致。
- 输出：实际文件清单、冲突点。

### 2. 修改前确认阶段

当前 Role：`developer`

- 对照 `需求范围`、`非目标`、`执行约束`。
- 有冲突先停并说明，不开始改代码。

### 3. 实现阶段

当前 Role：`developer`

- 只改列入范围的文件和函数。
- 按函数级伪代码落地，风格跟随周围代码。
- 不新增方案外抽象。

### 4. 自检阶段

当前 Role：`developer`

- 逐条勾 `验收标准`。
- 检查是否出现方案外重构、格式化或无关文件。

### 5. 运行验证阶段

当前 Role：`developer`

- 只执行 `运行验证方式` 中的命令或操作。
- 记录命令、结果、失败原因；环境不可用时写明缺什么。

### 6. 静态校验阶段

当前 Role：`code-requirement-verifier`

- 按 `代码静态校验` 出报告。
- 本阶段不修改代码。

### 7. 最终交付阶段

当前 Role：`developer`

- 按 `最终交付要求` 汇总。
- 写清与方案骨架的偏差和剩余风险。
```

交付前必须对照已解析角色目录核实这些默认 Role 索引。每一步都应可执行。开头应包含阅读现有代码和确认契约，结尾应包含验收对照和校验报告。角色行只是当前阶段的局部执行框架；方案切换阶段后，前一阶段角色不得继续影响后续阶段。

### 验收标准

写成可判断真假的条目。每一项都应能标记为 `已满足` / `未满足` / `部分满足`。

使用以下基线内容，并只按任务实际情况调整检查项：

## 运行验证章节

`运行验证方式` 必须来自实际任务上下文，只包含相关验证路径。

根据场景选择：

- 纯逻辑或类库改动：构建受影响项目，运行单元测试；风险合适时补充聚焦测试。
- WPF/UI 改动：构建受影响 GUI/模块项目；可行时手动打开页面，验证绑定、命令、视觉状态、权限和错误提示。
- 服务改动：构建受影响服务，运行聚焦服务测试或集成测试，验证日志、配置、启动和关键请求/命令路径。
- 设备/PLC/机器人/IO 改动：说明模拟器、夹具、dry-run、手工回归、安全互锁、重启和操作员验证要求。不要假装已经具备完整硬件验证环境。
- 配置改动：校验 JSON/XML 语法、键名、服务重启要求、默认值兼容性和手工启动检查。
- 数据库/存储改动：校验 schema/字段映射、迁移/回滚路径、读写兼容和数据保留风险。

如果运行环境不可用，也要写清楚未来可运行时的验证步骤，并明确哪些检查必须等待可运行环境。

6. 执行约束遵守情况。
7. 使用已解析角色目录中精确 Role 索引的阶段角色执行摘要，包括任何无法按文档角色执行的阶段。

## 最终检查

完成方案文档前，确认：

- 第一屏能说明这份方案是用来做什么的，以及推荐由哪个 executor 执行。
- 方案是填好的 `源码修改执行方案模板.md`，不是论文或自创目录。
- 执行者能判断：改哪些文件、改哪些函数、不能动什么、怎样算做完。
- 方案元信息填写了具体值，或有理由地写了 `待确认`。
- 需求范围、非目标和执行约束能限制不必要改动。
- 阶段角色是局部阶段说明，并且不与执行约束冲突。
- 每个阶段角色都使用已解析角色目录中的精确索引，并且已核对所选角色文档适合该阶段。
- 没有合适索引角色时已经停止编写并询问用户，而不是向用户交付自行创造的角色。
- 修改范围是结构化的，executor 容易读取。
- 每个新增类或结构体都包含文件、命名空间、声明、职责、依赖/状态解释、生命周期、新增原因和框架级类型骨架；没有新增类型时已明确说明。
- 新增类型骨架中的每个可调用成员都同时出现在 `函数级修改设计` 中。
- 每个受影响源文件都列出了需要修改的现有函数和需要新增的函数；不涉及函数的修改已经明确说明。
- 每个关键修改函数或新增函数都包含覆盖主要控制流的框架级伪代码，但没有嵌入最终实现。
- 每个函数级设计都映射到 `修改范围` 中的文件，并且没有把格式案例误写成仓库事实。
- 实现步骤分阶段、有顺序且可执行。
- 验收标准是可判断真假的检查项。
- 静态校验是强制要求，并包含报告格式。
- 运行验证是任务相关的，不是通用填充内容。
- 风险区分了假设、只能静态确认的不确定性、只能运行确认的不确定性。
- 执行入口提示明确引用 `$ai-plan-executor`。
- 文档不包含 TODO 占位，除非明确要求 executor 在编辑代码前补齐这些 TODO。
